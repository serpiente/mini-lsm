&self is shared, not immutable

Why SkipMap mutates through a shared reference and BTreeMap refuses to — and why the answer is decided by memory layout, not by taste.

01The signature that looks like a typo

Open src/mem_table.rs in your starter. The method you have to implement today is this:

/// Put a key-value pair into the mem-table.
pub fn put(&self, _key: &[u8], _value: &[u8]) -> Result<()> {
    unimplemented!()
}
mini-lsm-starter/src/mem_table.rs — the MemTable you are implementing

A method that inserts data and takes &self. If your model of Rust is "& means read-only", this signature is impossible, and the rest of Week 1 will feel like it is getting away with something. It isn't. Fixing one word in your mental model makes the whole write path obvious.

The word to drop

"Immutable reference" is a misleading name for &T. It is everywhere — including in the Mini-LSM book — so you are in good company using it. But it describes a consequence that only usually holds, not the guarantee.

02The reframe

Rust has two reference types, and the axis that separates them is how many may exist at once:

&T — shared

Many may exist simultaneously. Aliasing is allowed.

Says nothing about whether the referent changes.

&mut T — exclusive

Exactly one may exist. Nothing else may alias it.

Its real power is the exclusion, not the mutation.

The invariant the compiler actually enforces is not "shared things never change." It is no aliasing and mutation at the same time. The Rustonomicon puts the guarantee plainly: &mut isn't allowed to be aliased — and that is what lets the compiler cache reads in registers and reorder writes.

→ Rustonomicon: Aliasing

So there are exactly two ways to legally mutate something in Rust:

  • Prove you are alone. Hold a &mut T. The borrow checker verifies exclusivity at compile time.
  • Make the mutation safe to alias. Route it through UnsafeCell, the one primitive permitted to change behind a &T. This is called interior mutability. Every atomic type, Mutex, and RefCell is built on it.
→ std::cell::UnsafeCell · Rust Book 15.5

Neither map gets to choose freely. Each one's memory layout decides which door is open to it. That is your actual question — so let's look at the two layouts.

03BTreeMap: elements live in arrays, and arrays move

Rust's BTreeMap is a B-tree with a small, fixed branching factor. From the standard library's own source:

const B: usize = 6;
pub(super) const CAPACITY: usize = 2 * B - 1;          // = 11
pub(super) const MIN_LEN_AFTER_SPLIT: usize = B - 1;   // = 5

struct LeafNode<K, V> {
    parent: Option<NonNull<InternalNode<K, V>>>,
    parent_idx: MaybeUninit<u16>,
    len: u16,
    keys: [MaybeUninit<K>; CAPACITY],   // 11 keys, inline
    vals: [MaybeUninit<V>; CAPACITY],   // 11 values, inline
}
library/alloc/src/collections/btree/node.rs, lines 43–66 — run rustc --print sysroot to find your copy

Read those two highlighted lines carefully, because they decide everything. The keys and values are stored inline, in fixed arrays, eleven to a node. They are not boxed, not behind pointers — they are bytes sitting in the middle of the node allocation.

Hence the signature, and it could not be otherwise:

pub fn insert(&mut self, key: K, value: V) -> Option<V>
library/alloc/src/collections/btree/map.rs, line 1045

04SkipMap: elements never move, so pointers can be swapped

Now the other layout. A crossbeam_skiplist node is one heap allocation per entry, carrying a variable-height "tower" of atomic forward pointers:

const HEIGHT_BITS: usize = 5;
const MAX_HEIGHT: usize = 1 << HEIGHT_BITS;   // = 32 levels

#[repr(C)]
struct Node<K, V> {
    value: V,
    key: K,
    /// Reference count AND tower height, packed into one word.
    refs_and_height: AtomicUsize,
    tower: Tower<K, V>,   // [Atomic<Node<K, V>>] — dynamically sized, must be last
}
crossbeam-skiplist-0.1.3/src/base.rs, lines 16–90 — ls ~/.cargo/registry/src/*/crossbeam-skiplist-0.1.3/src/

Each node's height is drawn at random when it is created — a xorshift PRNG, then trailing_zeros() + 1, which gives each extra level a probability of ½. Tall nodes are rare and act as express lanes; a search starts at the highest occupied level and descends. That randomness is what replaces a B-tree's careful rebalancing: nothing is ever rebalanced, because nothing needs to be.

base.rs, random_height at line 558 · search_bound at line 681

Here is that exact moment in the real source, stripped to its spine:

// Set the lowest successor of `n` to `search.right[0]`.
n.tower[0].store(search.right[0], Ordering::Relaxed);

// Try installing the new node into the skip list (at level 0).
if search.left[0][0]
    .compare_exchange(search.right[0], node, SeqCst, SeqCst, guard)
    .is_ok()
{
    break;    // published. the key is now visible to every thread.
}
// Lost the race against another writer — re-search and try again.
crossbeam-skiplist-0.1.3/src/base.rs, ~lines 925–940

Every mutation goes through Atomic<Node<K, V>>, which is built on UnsafeCell. Door number two. So the signature can be — and is:

pub fn insert(&self, key: K, value: V) -> Entry<'_, K, V>
crossbeam-skiplist-0.1.3/src/map.rs, line 372
The whole lesson in two sentences

BTreeMap keeps elements in inline arrays that relocate when a node splits, so the only safe way to mutate it is to prove nobody else is looking — &mut self.

SkipMap keeps every element in its own allocation, joined by atomic pointers, so a complete structural update is one compare_exchange and nothing relocates — which is legal through &self.

05What you just bought, in your own code

This is not trivia; it is the reason today's task is short. Because put takes &self, the Mini-LSM book can say:

The important difference is that mutating methods such as insert require only an immutable reference to the skiplist, rather than a mutable one. […] Your memtable implementation therefore does not need an additional mutex.

→ Mini-LSM Week 1 Day 1: Memtable

Concretely: a writer takes only a read lock on the engine's state to get at the current memtable, then inserts. Many writers do this at once. The write lock is reserved for structural changes — swapping in a fresh memtable when the current one is full. Had SkipMap::insert needed &mut self, every single put would have had to serialise behind an exclusive lock, and the memtable would be the engine's bottleneck.

06Practice

Answer from memory. Scrolling up costs you the benefit.

What does holding a &T actually guarantee?

  • The referent will never be modified by anyone
  • The referent may be accessed by many holders
  • The referent lives inside a single owning thread
  • The referent must be copied before any change

Why must BTreeMap::insert take &mut self?

  • A full node splits, so existing elements physically move.
  • A sorted map cannot ever allow two concurrent writers.
  • A generic parameter forces the stricter of both signatures.
  • A tree lookup already borrows the root node mutably.

Because SkipMap::insert takes &self, what does your MemTable not need?

  • Its own mutex guarding the inner map
  • Any heap allocation for the stored keys
  • A stable ordering over the stored keys
  • One atomic counter tracking approximate size

Now produce it, don't recognise it.

In your own words: name the layout fact for each map, and the signature it forces. Two sentences is enough — but write them before revealing.

Model answer

BTreeMap stores up to 11 keys and values in inline arrays inside each node, so an insert into a full node splits it and physically copies elements into a new allocation; any outstanding reference would dangle, so insert must take &mut self to prove no such reference exists.

SkipMap stores each entry in its own allocation, linked by a tower of atomic pointers, so an insert allocates a node and publishes it with a single compare_exchange while nothing else moves; that mutation goes through UnsafeCell-backed atomics, so insert can take &self.

Credit yourself if you said relocation (or "elements move") for the first and atomic pointer swap (or "nothing moves") for the second. Those are the load-bearing facts; the constants are lookup-able.

07One loose thread, deliberately left

You may have noticed that SkipMap::get does not return Option<&V> the way BTreeMap::get does. It returns Option<Entry<'_, K, V>>. Ask yourself why before the next lesson: if another thread can remove a node at any instant, what stops the node you are reading from being freed under you? The answer is hiding in that refs_and_height field you saw in Node, and it is the subject of lesson 02.
